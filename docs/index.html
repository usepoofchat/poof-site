Poof documentation

A chatroom that forgets.

Poof is a private chatroom that lives in a browser tab. No account, no phone number, no email. You open a quant-room, share it, talk. When the timer runs out, the quant-room is gone. Poof.

These docs explain what Poof is, why it exists, how it works, what it protects you from, what it does not, and how you can check every claim yourself.

About & philosophy

Less data, by design.

Privacy is not only about hiding information. It is also about reducing how much information exists in the first place.

Storage is cheap, so most of the internet keeps everything, just in case. Every message, contact list and login stays on someone's server for years. Each of those copies is something that has to be protected, forever.

Poof starts from the opposite default. A conversation exists for as long as people are having it, and not much longer.

Honest footnote

Keeping less does not make a system secure on its own. It removes some risks completely: a breached database, a subpoena for old messages, someone decrypting an archive years from now. Other risks stay exactly where they were, like a compromised phone or someone taking a screenshot. The threat model lists both.

Privacy is not the same as security

IdeaThe question it answers

Poof is built around confidentiality and ephemerality. It helps with privacy because it never asks who you are. It is not an anonymity tool on its own: the network still sees which IP addresses connect, and when.

Create, use, expire, poof Concept

Grass grows, exists for a season, then returns to the soil. Nothing about it is meant to last forever, and that is not a flaw. Poof treats a conversation the same way.

An analogy, not a security proof. What actually expires, and where, is described in Data lifecycle.

Why “Poof”?

Because that is what the quant-room does at the end.

How it works

The life of a quant-room.

1 · Create

When you press Create Quant-Room, your browser first makes a random 32-byte creator secret. It keeps the secret in this tab and sends Poof's server only its SHA-256 fingerprint. The server answers with a fresh quant-room id (16 random bytes) and the moment the quant-room ends, 10 minutes later.

Only after that answer does your browser generate the quant-room key: 32 random bytes from the browser's own Web Crypto API. The key is made in your tab, after the server has already spoken, so there is no request it could ever travel in.

Anatomy of a quant-room link

Everything after the # is the link's fragment. Browsers never put the fragment in a request. Your browser reads the room id from it and tells Poof's server which room to open, but the key next to it stays in the tab. Poof's server never receives the key, so it can never read the quant-room.

the creator secret is not in the link

Only the browser that created the quant-room holds it, in its local storage, and only until the quant-room ends. That's how the server knows who may press Poof it now, even after a reload, without ever knowing who you are. The quant-room key is kept apart from it, in this tab only.

How four words become a link

The four words come from a fixed list of 2,048 everyday words, so a phrase holds 44 bits of chance. Your browser stretches it with PBKDF2-SHA-256 over 200,000 rounds and splits the result into two things: a mailbox address and a lock key. It locks the quant-room link with AES-256-GCM and leaves only the locked copy at that address.

Your guest types the same four words, in any case, separated by spaces, dashes or commas. Their browser repeats the derivation, finds the mailbox and opens it. Opening it empties it on the spot, and an unread mailbox disappears after 3 minutes. Poof's server sees an address and a locked blob, never the words: every guess would cost 200,000 rounds across about 17.6 trillion possible phrases, far longer than a phrase lives.

The opened link must point to usepoof.chat and be a well-formed quant-room link, so a tampered mailbox can't send your guest anywhere else.

3 · Connect

To find each other, the two browsers swap connection details through Poof's server. This is signaling: the server relays them, stamps who sent what, and stores none of it. It also holds the door. A Quant-Room has two seats, the server decides who gets one, and a third visitor is turned away.

Once a direct WebRTC data channel is open, the browsers run a post-quantum key exchange over it, mix the result with the quant-room key, and prove to each other that they arrived at the same keys. Only then does the quant-room switch to sealed and the message box opens. If the proof fails, the connection is refused instead of downgraded.

If the two networks can't reach each other directly, traffic goes through a relay over TLS. The relay forwards encrypted bytes it can't read, and its credentials are issued only once two people are paired and stop working when the quant-room ends.

4 · Talk

Every message is encrypted in your browser with AES-256-GCM before it leaves, using a key that only travels in your direction, and it carries a sequence number. Your guest's browser checks that number: a message that was altered, replayed, dropped or reordered closes the connection instead of slipping through. Poof's servers are not on the message path at all.

Messages hold up to 5,000 characters. Each person gets a default name, like Amber Fox, that looks the same on both screens until they pick their own (up to 32 characters). The “typing…” hint travels the same encrypted way and carries no text. The developer guide shows every byte of a message on the wire.

How a group stays private

There is no group key. Every pair of people in a Super Quant-Room builds its own direct connection and runs its own post-quantum handshake, exactly as in a Quant-Room for two. When you send a message, your browser encrypts it once for each person, with that pair's keys, and sends it down each connection. Ten people means 45 separate encrypted links.

Poof's server still only holds the door: it decides who gets one of the paid seats, and nobody can squeeze in once the room is full. People can leave and come back while the room lives. The quant-room goes on until its timer ends or the creator ends it. If two people briefly see a different list of who's inside, for example while someone is still joining, the room shows it instead of hiding it.

Files

Drop files onto the chat or pick several at once. Images show a preview right in the conversation. Each file is cut into pieces of 16 KiB, every piece is encrypted on its own and travels over a separate encrypted channel for files, to each person in the room. The receiving browser checks the size, the number of pieces and finally the SHA-256 fingerprint of the whole file. Only then does it show as delivered.

An uncensored AI model

When you create a Super Quant-Room you can add an uncensored AI model to it. Talk to it alone, in a quant-room just for you, or bring it into a group: in a room with other people, start a message with @ai to ask it something.

The model runs inside a sealed hardware enclave (Intel TDX) hosted by an AI infrastructure partner. Your browser encrypts the conversation straight to the enclave. Poof's servers only pass the encrypted text along, and nobody outside the enclave, Poof included, can read it.

Before anything leaves your browser, it asks the enclave for a fresh proof of what it is running, checks that the proof covers the model's key, and only then encrypts to that key. The answer streams back encrypted to your browser, which decrypts it and shares it with everyone in the room over the same encrypted links as any message.

what changes with the AI on

To answer, the model has to read. When someone asks it a question, their browser sends the recent conversation along with it, so the model sees what was said in the room. It keeps no logs and no memory between quant-rooms, and it leaves when the timer ends. Without the AI, nothing changes: no server ever sees your messages. One honest limit: your browser checks what the enclave's proof says, while Intel's signature on that proof is confirmed by the hosting partner, not yet by your browser.

The payment and the quant-room stay apart through blind signatures. Before you pay, your browser prepares a random one-time pass and “blinds” it. Poof reads the payment straight from the blockchain. While it's still confirming, the answer is “pending” and your browser simply asks again. Once it counts, Poof signs your blinded pass, without being able to see it, and your browser unblinds the signature. Now you hold a pass that Poof can recognise as its own, but has never seen.

5 · Spend it

Your browser uses the pass to create a Super Quant-Room, or to upgrade the one you're in. Poof checks its signature, records that this pass is used up, and opens the room. Each pass works exactly once.

How a blind signature works

Picture a letter sealed in an envelope lined with carbon paper. Poof signs the outside of the envelope after checking your payment. The signature presses through onto the letter, but Poof never sees the letter. Later you show the letter on its own: the signature on it is clearly Poof's, yet Poof has no way to tell which envelope it signed.

In technical terms, Poof uses RSA blind signatures (RFC 9474, the RSABSSA-SHA384-PSS-Randomized variant), with one signing key per variant, so a pass is worth exactly what was paid for it. Each key's id is its own fingerprint, and your browser checks it, so a key can't be passed off under another key's name. The blinding factor, the one secret that could connect the two ends, never leaves your browser.

How a question travels

1-3 · The proof comes first

Before a single word leaves your browser, it sends the enclave 32 fresh random bytes and asks for a proof of what it is. The proof comes back signed into the hardware's own report, and your browser checks it:

  • it's a report from an Intel TDX enclave;
  • the enclave doesn't run in debug mode, where its memory could be read;
  • the report contains the model's key, so that key lives inside this enclave;
  • the report contains your 32 random bytes, so it was made just now, for you;
  • it's the model Poof uses, and nothing else.

If any check fails, nothing is sent.

4-5 · Encrypted both ways

Your browser encrypts the question to the model's key with a fresh one-time key for every message (elliptic-curve key agreement, HKDF-SHA-256 and AES-256-GCM). It also sends a temporary key of its own, and the enclave encrypts every piece of the answer to it. Poof's server forwards the ciphertext both ways and turns away anything that isn't encrypted. Your browser does the same: an answer that arrives unencrypted is refused.

Who may ask

Anyone who is in the quant-room. Each browser derives an AI token from the quant-room key, and the creator registers only the token's fingerprint with Poof. Poof can check that a question comes from someone with the link, without ever learning the key.

What the model sees

To answer well, the model needs the conversation. With each question, the asking browser sends the recent messages along, oldest dropped first, up to about 120 KB of text, with each line marked by the speaker's name. Poof's instructions to the model are public and only explain the format:

Relays today

Two different things in Poof are called a relay. Neither one ever holds a key.

RelayWhat it carriesWhat it never carries

Direct, or via a relay

Every link tries a direct path first. Each browser learns its public address from a STUN server, and the two swap candidates through the signaling relay. If a direct pair works, traffic goes straight from one browser to the other.

Some networks don't allow that: strict office firewalls, some mobile carriers, routers that change your address for every connection. Then the link goes through the relay. Poof only hands out the relay's TLS address, so relayed traffic looks like ordinary encrypted web traffic on the wire.

What the quant-room shows

Once a link is sealed, the status line says sealed · direct or sealed · via relay. Your browser reads which network path the connection picked. If either side goes through the relay, or it can't tell, it says relay: the careful answer. The two browsers also tell each other what they saw, and relay wins. In a group, one relayed link is enough for the quant-room to say via relay.

Credentials that run out

  • Relay credentials are issued only when two people are paired, never from a public endpoint.
  • They last as long as the quant-room has left: at least 60 seconds, at most 24 hours. Nobody holds a working relay credential after the quant-room is gone.
  • When a quant-room becomes a Super Quant-Room, everyone gets fresh credentials for the new end time, and relayed links reconnect with them before the old ones run out.
  • Only TLS relay addresses are handed out. Plain UDP and TCP relay addresses are dropped.

If relay credentials can't be issued within 3 seconds, the quant-room carries on with direct links only. On networks that allow a direct path nothing changes. On networks that don't, people can't connect until the relay answers again.

Relay nodes: what comes next

coming next

Not live yet. Today every relayed connection goes through one infrastructure provider.

One provider means one place that sees which IP addresses talk through it, and one dependency if it has a bad day. Relay nodes spread that out: independent relays, run by more operators, so no single company carries all of Poof's relayed traffic.

What won't change

These hold because of how the encryption works, not because of who runs the relay:

  • A node forwards encrypted bytes. End-to-end encryption and the hybrid key stay exactly as they are, and a node never gets a key.
  • A node can't alter, replay or reorder anything without the link closing.
  • Credentials stay short-lived and tied to one pairing.
  • Direct links stay the first choice. A node only carries traffic when a direct path fails.

What a node will still see

The same as today's relay: IP addresses, timing and volume. Spreading relays out lowers how much any one operator sees. It doesn't make relayed traffic anonymous.

Before it ships, this page will say

  • how your browser picks a node;
  • how a node that misbehaves is spotted and dropped;
  • where the node code lives, open source like the rest of Poof.

  • A direct link shows your IP address to the other person. Their browser connects to yours, the way any direct connection does. There's no relay-only switch in quant-rooms today. Use a VPN if you need to hide your address.
  • A relay sees who is connected. Not what is said, but which addresses, when, and how much.
  • A relay can refuse service. It can't read or change your traffic, but it can stop carrying it, and the link ends.

Quantum, part 1

What happens to today's secrets when tomorrow's computers arrive?

Encryption is a bet that some maths problems are too hard to solve. Quantum computers change which problems are hard. This page explains how, without the hype.

Bits and qubits

A normal bit is 0 or 1. A qubit can be in a combination of both, called superposition, until you measure it, and then it becomes a plain 0 or 1. Quantum algorithms use quantum gates to arrange those combinations so that wrong answers cancel out and right answers become likely when you measure. That is not “trying every answer at once”. It only helps for problems with special structure. Try it in the Quantum Lab.

Two kinds of encryption, two kinds of risk

Public-key cryptography (RSA, elliptic curves, ECDH key exchange, digital signatures) lets two strangers agree on a secret. It relies on problems like factoring large numbers or computing discrete logarithms. Symmetric cryptography (AES) encrypts the actual data once both sides share a key. It relies on the key simply being too big to guess.

A picture of the idea, not a description of how Shor's algorithm works inside. Concept

So the weak spot is the handshake

The data itself (AES-256) holds up well. The vulnerable moment is when two parties agree on a key with RSA or elliptic curves. If someone can later recover that key exchange, they can unlock everything it protected.

Today vs tomorrow

No quantum computer is publicly known to break RSA or elliptic-curve keys at the sizes used on the internet. That would take a large, error-corrected machine, often called a “cryptographically relevant quantum computer”. Nobody can give a reliable date for one. The reason to act now anyway is on the next page.

Quantum, part 2

Harvest now, decrypt later.

You do not need a quantum computer today to attack today's messages. You only need to record them and wait.

Anyone who can watch a network (an internet provider, a compromised router, a state agency) can save encrypted traffic cheaply and keep it for years. If that traffic relied only on RSA or elliptic-curve key exchange, a future quantum computer could unlock it. For conversations that must stay private for a long time, the risk starts the day they are recorded.

How Poof answers it

Ephemerality alone is not enough. Poof deleting things does not stop someone else from recording traffic on the network. That is why the encryption itself holds up against future quantum attacks, which is the job of the hybrid post-quantum key. See it play out in the Quantum Lab.

What this does not solve

  • A compromised device. If your phone or browser is infected, messages can be read before they are encrypted.
  • The link. The classical half of the key travels in the quant-room link. Someone who captured the link and broke the post-quantum exchange could read the quant-room. Both are needed.
  • Metadata. A recorder still sees that two IP addresses talked, when, and for how long.

Quantum, part 3

Two locks on every quant-room.

Post-quantum cryptography is ordinary software that runs on today's devices, built on maths problems believed to be hard even for quantum computers.

The NIST standards

In 2024 the U.S. National Institute of Standards and Technology published the first post-quantum standards:

StandardNameJobBased on
FIPS 203ML-KEMAgreeing on a shared keyModule lattices
FIPS 204ML-DSADigital signaturesModule lattices
FIPS 205SLH-DSADigital signaturesHash functions only

Poof uses ML-KEM-768 for its key exchange.

What a KEM does Concept

A key encapsulation mechanism works like a lockbox. Your guest publishes an open padlock (public key). You put a random secret in a box, snap the padlock shut and send it (ciphertext). Only your guest has the key that opens it. Now you both share the same secret, and anyone who watched only saw a locked box.

ML-KEM-768 in numbers

ItemML-KEM-768For comparison: X25519
Public key1,184 bytes32 bytes
Ciphertext1,088 bytes32 bytes
Shared secret32 bytes32 bytes
Security levelNIST category 3Not quantum-resistant

The keys are bigger, but for a chat handshake a couple of kilobytes, once per quant-room, makes no noticeable difference.

Why hybrid

Post-quantum algorithms are newer than RSA or elliptic curves. A hybrid design does not bet everything on one of them: it combines a classical secret with a post-quantum one, so an attacker has to break both.

Both secrets go into HKDF-SHA-256 together, as one input, with a fixed, versioned Poof label and a hash of the whole exchange: the room, the two people, the public key and the ciphertext. The result stays secret as long as either half does. From it each side derives one key per direction and a confirmation key. Before any message, both browsers prove they arrived at the same result with an HMAC-SHA-256, each side using its own label, so a confirmation can't simply be bounced back. A tampered handshake fails this check and the connection is refused. Every label is on the developer guide.

Implementation notes

  • In the browser. Browsers don't ship ML-KEM yet, so Poof uses a pinned open-source implementation bundled into its engine, never fetched from a third-party server at runtime. AES-GCM, HKDF and HMAC come from the browser's own Web Crypto API.
  • Side channels. The ML-KEM library is written to avoid secret-dependent branches, and MAC checks go through Web Crypto, which compares in constant time. JavaScript in a browser can't promise strict constant time for everything, so the hybrid design never relies on one half alone.
  • Signatures. Poof does not use post-quantum signatures. Quant-room integrity comes from the shared keys and key confirmation, not from long-term identities.

From click to sealed

The server pairs people by itself. When someone joins, it sends paired to both sides, with a role and the relay credentials. The member who joined first is the initiator: it makes the WebRTC offer and starts the key exchange. The server stamps the sender of every signal itself, from the socket it came on, so nobody can pretend to be someone else in the room. In a group, every pair goes through steps 6 to 10 on its own.

The hybrid handshake

The handshake runs inside the DataChannel, before any chat. Both sides mix two secrets: K_C, the 32-byte quant-room key from the link, and SQ, the shared secret from ML-KEM-768. The derivation is bound to everything the two sides just exchanged:

Putting both secrets into the same input is the standard hybrid combiner: K stays secret as long as either K_C or SQ does. Binding the room id and both member ids into T means a handshake can't be replayed or spliced between a different pair of people. Each side checks the other's MAC in constant time. If a check fails, the connection is refused, never quietly downgraded.

honest limit

Someone who doesn't have the link can't derive K, so even a hostile server sitting in the middle fails the MAC check. Someone who does have the link could run two separate handshakes, one with each of you, and both would pass. Comparing the safety code on two screens would expose that. The engine already derives it; the room doesn't show it yet. Until it does, share the link only with the person it's meant for.

Frames on the wire

After the handshake every message is a binary frame. Each direction has its own key and each channel its own counter, starting at 0 and going up by exactly 1. The receiver rebuilds the nonce from the header and checks the counter before decrypting. DataChannels are ordered and reliable, so any gap, repeat or reflection can only be tampering: the link is closed.

Rules the code keeps

  1. Keys are made in the browser and stay there. The room key lives in the link's fragment and in memory, never in a request, a header or a log.
  2. The server never sees content. Chat, files, file names and names travel only as end-to-end encrypted frames.
  3. Signaling is a relay, not a transport. Chat never goes over the WebSocket, not even as a fallback.
  4. The server enforces capacity. It decides who gets a seat; a client can't talk its way past it.
  5. Quant-rooms are ephemeral. Server state is deleted when a room expires or ends.
  6. Logging stays off. The API writes no logs, and there are no analytics, cookies or third-party scripts.
  7. The API stays narrow. Only usepoof.chat may call it from a browser, and it serves nothing but /api/* and /ws/*.
  8. Every input has a limit, a schema, and tests that go past it.
  9. The client doesn't trust the server for resources. Peer counts, file sizes and relay lists are capped in the browser too.
  10. Wire changes are versioned. Any incompatible change bumps the protocol version.
  11. Builds are reproducible and attested. Same commit, same bytes. See Verify it yourself.

Running it locally

Open http://localhost:5173 in two browser profiles (or one normal and one private window) and create a quant-room between them. The page shows the status, whether the path is direct or relayed, the chat and the raw log of the handshake. Add ?relay=1 before the # to force the connection through the relay.

Rooms

The key is not part of any of this. The browser generates it after this answer arrives and keeps it in the link's fragment. GET /api/rooms/:id returns the same fields plus peers, the number of people inside. tier is free, 60m or 24h.

The server checks the secret against the fingerprint it was given at creation. The new lifetime starts now, seats only go up, and everyone in the room gets room.upgraded.

Four-word mailboxes

The blob is at most 2 KiB and lives for 3 minutes. take returns and deletes it in one step, so the second attempt gets handshake_not_found. An id that already holds a blob can't be filled again until it's taken or expires (handshake_exists).

Payments

Variants are written lifetime-people, with -ai when the AI model is included: 3600-4, 86400-10-ai. The whole flow is on the Payments page.

AI model

All three calls carry the room id and the room's AI token, which the browser derives from the quant-room key. /api/ai/chat accepts only hex ciphertext, forces the model and its settings, and streams the encrypted answer back untouched. See The AI model.

The WebSocket

Connect to wss://api.usepoof.chat/ws/rooms/:id?peerId=<22 characters>. The peer id is random per session and stays the same across reconnects. Messages are JSON text of at most 32 KiB, each carrying "v": 1. A plain ping every 20 seconds gets a pong; no answer within 8 seconds means the socket is dead. Glossary.

Every term in three steps: plain words, the technical version, and why it matters to Poof.

Qubit

simpleA bit that can be 0, 1, or a mix of both until measured.

technicalThe basic unit of quantum information, described by complex amplitudes; measurement yields a classical bit.

for poofLarge numbers of reliable qubits are what would threaten today's key exchanges.

Superposition

simpleBeing in a combination of states at once.

technicalA qubit state is a linear combination of basis states.

for poofIt's why quantum algorithms can do things classical ones can't, for some problems.

Entanglement

simpleQubits whose results are linked, however far apart.

technicalA joint state that can't be written as separate per-qubit states.

for poofA resource quantum algorithms rely on.

Quantum gate

simpleAn operation that changes qubits.

technicalA unitary transformation applied to one or more qubits.

for poofAlgorithms like Shor's are sequences of gates.

Physical vs logical qubit

simpleRaw hardware qubits vs error-corrected ones built from many of them.

technicalError correction encodes one logical qubit across many noisy physical qubits.

for poofBreaking RSA needs many logical qubits, which is why it isn't possible yet.

Quantum error correction

simpleFixing quantum errors without looking at the data.

technicalCodes that detect and correct errors on encoded qubits.

for poofThe main engineering hurdle between today's machines and dangerous ones.

Quantum advantage

simpleA quantum computer beating classical ones at some task.

technicalDemonstrations exist for specific, mostly artificial problems.

for poofNot the same as breaking encryption. Headlines often mix them up.

Shor's algorithm

simpleA quantum recipe for factoring and discrete logarithms.

technicalPolynomial-time algorithm for integer factorization and discrete log.

for poofBreaks RSA and elliptic-curve key exchange on a big enough machine.

Grover's algorithm

simpleA quantum speed-up for searching.

technicalQuadratic speedup for unstructured search.

for poofWeakens symmetric keys; AES-256 stays strong.

Post-quantum cryptography

simpleEncryption designed to resist quantum attacks, running on normal computers.

technicalSchemes based on problems like lattices or hash functions.

for poofPoof's handshake uses it (ML-KEM-768).

Quantum-safe

simpleExpected to hold up against quantum computers.

technicalInformal term; depends on assumptions and correct implementation.

for poofWe say “designed to resist”, never “unbreakable”.

Harvest now, decrypt later

simpleRecord encrypted data today, unlock it later.

technicalStore-and-wait attack against long-lived ciphertext.

for poofThe reason post-quantum matters before quantum computers exist.

KEM

simpleA way to agree on a shared secret using a public key.

technicalKey encapsulation mechanism: encapsulate / decapsulate.

for poofHow Poof's browsers agree on the post-quantum half of the key.

Lattice cryptography

simpleMaths based on hard problems in multi-dimensional grids.

technicalSecurity from problems like Module-LWE.

for poofThe foundation of ML-KEM and ML-DSA.

ML-KEM

simpleThe NIST-standard post-quantum key exchange.

technicalFIPS 203, module-lattice KEM; ML-KEM-768 is NIST category 3.

for poofPoof uses ML-KEM-768.

ML-DSA

simpleThe NIST-standard lattice signature scheme.

technicalFIPS 204.

for poofNot used by Poof.

SLH-DSA

simpleA signature scheme built only on hash functions.

technicalFIPS 205, stateless hash-based signatures.

for poofNot used by Poof.

Forward secrecy

simpleOld conversations stay safe even if a key leaks later.

technicalSession keys are ephemeral and not derivable from long-term keys.

for poofEach Poof quant-room uses fresh keys that disappear with the quant-room.

URL fragment

simpleThe part of a link after #.

technicalNot sent to the server in HTTP requests.

for poofWhere Poof keeps the classical quant-room key.

WebRTC

simpleBrowser technology for direct connections.

technicalPeer-to-peer media and data channels with DTLS encryption.

for poofHow messages travel between browsers without Poof's servers.

TURN relay

simpleA fallback server that forwards traffic when a direct link fails.

technicalRelays packets; sees only encrypted payloads.

for poofLets quant-rooms work behind strict networks.

HKDF

simpleA recipe for mixing secrets into a key.

technicalHMAC-based key derivation function (RFC 5869).

for poofCombines the classical and post-quantum secrets.

AES-GCM

simpleFast, standard encryption that also detects tampering.

technicalAuthenticated encryption with associated data.

for poofEncrypts every message in a quant-room.

Quant-room

simpleA temporary, private chatroom in Poof.

technicalA short-lived room on Poof's server that introduces browsers, plus end-to-end encrypted links between them.

for poofA Quant-Room lasts 10 minutes; a Super Quant-Room 1 hour or 24 hours.

Signaling

simpleIntroducing two browsers so they can connect.

technicalExchanging WebRTC offers, answers and ICE candidates through a server.

for poofPoof's server passes them along and stores nothing. Chat never goes this way.

DataChannel

simpleA direct pipe between two browsers.

technicalA WebRTC channel for any data, protected by DTLS.

for poofPoof opens two per pair, one for chat and one for files, each carrying its own encrypted frames.

Nonce

simpleA number used once.

technicalA per-message value that must never repeat under the same key.

for poofPoof builds it from a counter, so it never repeats and a missing message is noticed.

Key confirmation

simpleProving both sides got the same key, without showing it.

technicalEach side sends a MAC over the handshake transcript, under a key derived from the result.

for poofA failed check refuses the connection; it's never quietly downgraded.

Safety code

simpleA short code two people compare to rule out someone in the middle.

technicalA short authentication string derived from the session's keys.

for poofThe engine derives it; the quant-room doesn't show it yet.

PBKDF2

simpleA deliberately slow way to turn a password into a key.

technicalPassword-based key derivation with many rounds of HMAC.

for poofTurns four words into a mailbox address and a lock key, over 200,000 rounds.

Blind signature

simpleSigning something without seeing it.

technicalRSA blind signatures (RFC 9474): the signer signs a blinded message that only the requester can unblind.

for poofLets Poof sign a one-time pass without linking it to your payment.

One-time pass

simpleA ticket that works once.

technicalA blind-signed message, spent once and remembered only as a fingerprint.

for poofWhat a payment turns into, and what opens a Super Quant-Room.

Hardware enclave

simpleA sealed area inside a processor that even the machine's owner can't look into.

technicalA trusted execution environment, here Intel TDX, whose memory the hardware encrypts.

for poofWhere the AI model reads and answers.

Attestation

simpleA signed proof of what a machine is.

technicalA hardware-signed report that binds keys and fresh data to an enclave.

for poofYour browser checks one before it asks the AI anything.

Reproducible build

simpleThe same source always produces the same file.

technicalA deterministic build whose output can be hashed and compared by anyone.

for poofLets you match the live engine and API to the public code.

Questions.

39 short answers. Most link to a page with the full story.

What is Poof?

A private chatroom in your browser that doesn't ask who you are and disappears when the timer ends.

Why is it called Poof?

Because that's what the quant-room does at the end.

What does ephemeral mean?

Temporary by design. Quant-rooms have a fixed lifetime and nothing about the conversation is kept after it.

Do I need an account?

No. No email, no phone number, no username. Ever.

How long does a quant-room last?

A Quant-Room lasts 10 minutes. A Super Quant-Room lasts 1 hour or 24 hours.

How many people can join?

Two in a Quant-Room, up to ten in a Super Quant-Room, or just you with the AI model. The server holds the door, so nobody squeezes in once it's full.

How do I invite someone?

Send the link privately, show the QR code, or press Show a phrase and read out the four words. See How a quant-room works.

Is the four-word phrase secure?

For what it's for, yes: it works once and disappears after 3 minutes, and every guess costs 200,000 rounds of PBKDF2. Don't reuse it as a password.

What happens if I reload the page?

You go straight back into the quant-room. In a room for two, the other person's screen keeps the conversation for 30 seconds while you return.

What happens when the other person leaves?

The conversation is wiped from your screen at once. In a group, the room goes on without them.

What happens when the timer ends?

The connection closes and Poof's server deletes everything it held about the room. What's on your screen stays readable until you leave the page, then it's gone.

Can I end a quant-room early?

The person who created it can press Poof it now. It ends for everyone, and the server deletes it at once.

Can the creator remove someone?

Yes. That person is disconnected and can't come back into that room. The creator can also pin one message for everyone.

Can I send files?

In a Super Quant-Room, up to 2 MB per file. Files go browser to browser, encrypted piece by piece, and are checked on arrival. See Super Quant-Rooms.

Can Poof read my messages?

No. The key stays in your browser and Poof's servers never have it. Messages travel directly between browsers, already encrypted.

What does Poof's server know?

That a quant-room exists, how many seats it has, when it ends, and which IP addresses are connected while they are. Not what was said. See Data lifecycle.

What is stored after a quant-room ends?

Nothing about the conversation. See Data lifecycle.

Is Poof anonymous?

Not on its own. It never asks who you are, but networks can still see your IP address. Use Tor or a VPN if you need to hide that.

What's the difference between privacy and security?

Privacy is about who can learn things about you. Security is about whether data can be read or changed without permission. See Philosophy.

How do I pay for a Super Quant-Room?

From a wallet, in USDC on Ethereum, Base or Solana, or USDG on Robinhood Chain. No account. See Payments.

Can Poof link my payment to my quant-room?

No. Blind signatures give you a one-time pass Poof has signed but never seen, so it can't tell which payment a room came from. The payment itself is public on the blockchain, like any transfer.

Where does the money go?

To Poof's treasury, 0x68222E6dC73e161045233B2b76a47d98F84A7e8C. Once POOF is listed, the whole amount buys back POOF and burns it.

Can I talk to an AI in a quant-room?

Yes, in a Super Quant-Room: add the uncensored AI model when you create it (+$2 for 1 hour, +$5 for 24 hours). Talk to it alone, or start a message with @ai in a group. See The AI model.

Who can read what I ask the AI?

Only the model. It runs inside a sealed hardware enclave (Intel TDX) hosted by an AI infrastructure partner. Your browser encrypts the conversation straight to the enclave, and Poof's servers only pass the encrypted text along. To answer, the model reads the question and the recent conversation sent with it.

Is there mining or AI training?

No. Poof doesn't store conversations, and the AI model keeps no logs and no memory, so there's nothing to train on.

What is post-quantum cryptography?

Encryption designed to resist future quantum computers, running on today's devices.

Why should I care about quantum computers now?

Because traffic recorded today could be decrypted later. See Harvest now, decrypt later.

Can quantum computers decrypt messages today?

No machine is publicly known to be able to break today's key exchanges at real-world sizes.

What is Shor's algorithm?

A quantum algorithm that would break RSA and elliptic-curve key exchange on a large, error-corrected quantum computer.

What is ML-KEM?

The NIST-standard (FIPS 203) post-quantum way to agree on a key. Poof uses ML-KEM-768.

What is a KEM?

A key encapsulation mechanism: one side locks a random secret with the other side's public key.

Why hybrid instead of only post-quantum?

So an attacker has to break both a classical and a post-quantum secret. Neither alone is enough.

Can a hacked device still leak messages?

Yes. Encryption protects messages on the way, not on a compromised screen.

What if Poof's server is hacked?

It never has the keys or the messages. It could try to serve altered code, which is why the engine that holds your keys is open, signed and checkable. See Verify it yourself.

What if the relay (TURN) is compromised?

It only ever sees encrypted traffic and IP addresses.

Can the other person screenshot the chat?

Yes. No app can stop that.

Is Poof open source?

Yes, under the MIT licence: github.com/usepoofchat/poof-app. See Verify it yourself for how to check the build.

Is there an API?

Yes, a small one, and it never sees a key or a message. See API reference.

How do I report a security issue?

Privately, by email to security@usepoof.chat. See Responsible disclosure.
